## 3. E8 判定

| 基準 | 結果 | 判定 |
|---|---|:--:|
| (a) JSON着地 12/12 か | **12/12**・FORMAT_FAIL 0・`format_retry_used` **0件** | **合格** |

による複数セッション運用を前提とする——追補D本実施で実証済みの方式である。

### 速度の診断（記録・設計変更なし）

生成中の GPU を 2秒間隔6サンプルで測ったところ、**完全に安定して遊んでいた**:

```
utilization.gpu 18-19% / utilization.memory 1% / power.draw 52.1-54.7W（A100 SXM4 の TDP は 400W）
```

計算律速でもメモリ帯域律速でもなく、**ホスト側（CPU/Python）の1トークンあたりのオーバーヘッドが
律速している**。128エキスパート×48層の MoE を bitsandbytes 4bit で回す際の
エキスパート単位ディスパッチが原因の候補だが、**本パイロットでは機構を同定していない**（仮説）。

**対処は行わない**。理由は三つ:
1. transformers 4.57.6 は追補Dのピンと**同一**であり、追補D（647秒）の速度プロファイルを
   忠実に再現している。追補D凍結データは E1-1 の設計根拠であるから、環境を一致させる方が忠実である。
2. E1 が「生成条件は追補B/C/Dと同一。**一切変更しない**」を凍結している。
3. E1-2 が既に 129秒/647秒 の 4.3倍差を「実行環境の差」として織り込み、遅い場合の
   運用（resume）まで凍結している。**設計は既にこの事態を想定している。**

追補C（129秒）との差の機構は未解明のまま残す（3.2/D′ への申し送り事項）。

## 4. 破局分類の記述と、解釈の拒否（重要）

上表の破局判定を腕別に数えると **EB 1/3・Lneg 3/3・Onull 0/3・O 1/3** である。

**この数字から何も推論しない。** 理由:

1. **n=3/腕である。** 基底率を 45%（E1-1 のプール実測）と置けば、Lneg が 3/3 になる確率は
   単独で 0.45³ = 9.1%、Onull が 0/3 になる確率は 0.55³ = 16.6% であり、いずれも珍しくない。
2. **パイロットは登録された分析対象ではない。** 確証族（HE0・HE2）にも記述（HE1 等）にも算入しない。
   パイロットに検定を当てることは、それ自体が凍結規律の逸脱である。
3. **これは本プロジェクトが二度記録した過誤（#49・#52）の発火条件そのものである**——
   すなわち「結果を希望の方向に読む」引力が最も強く働く形（提案に有利な勾配が n 極小で現れた場面）。
   COI 規律により、**方向の言及そのものを本パイロットの結論から排除する**。

### COI 開示（FREEZE-RECORD に記帳すべき事項）

コーディネータは**ゲート実行前に、腕別の方向性をもつパターンに曝露した**（上記の 3/3 対 0/3）。
E9 のコーディネータ予想は FROZEN 本文に凍結済みであるから、この曝露が登録された予想を
遡って変えることはない。しかし、以後の裁定（とくに #O・#L転嫁 の採点裁定）において
アンカリングが働きうるため、事実として開示する。E5-4 の腕推測記録および E6-3(4)
（#O・#L転嫁 の裁定前に**系統外モデルの意見を必須で徴す**）は、この曝露に対する
既存の対抗措置として機能する。
