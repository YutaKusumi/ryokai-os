## 2. 新たに見えた三点（いずれも軽微・記録として）
### (a) 両者の JSON は**異なる経路**で作られています
| | `derived_table` の行キー | 由来 |
|---|---|---|
| 登録者 | `HW1, HW2, **K**, **F**` | **HTML/JavaScript の `table()`** |
| コーディネータ | `HW1, HW2, **K側**, **F側**` | **Python `derive_table()`** |
同じ器材が二つの実装（JS と Python）を持ち、**キー名が違います**。解析器はそれを見越した互換シム `r_.get('K側', r_.get('K'))` を持っています——**起草者は差を知っていたことになります。**
**帰結**: §7 の「両予想者はこの**三択で記入した**」は——**選択肢空間としては両者共通です** ✓（HTML も Python も同じ `FIELDS` から生成）。**しかし「同じ UI（HTML）で記入した」という含意までは、成果物からは支えられません。**
**これが効くのは一点だけ**——HTML UI は `confirm` チェックを強制し、器材の docstring はそれを **W′ の教訓（「とりあえず全部的中」を防ぐため、導出は自動・確認のみ人手）**と説明しています。**コーディネータが HTML を経由していないなら、その強制を通っていません。**
**ただし実害は無いと判定します。**私が両者の9行を凍結規則で再計算して不一致0でした——**確認の強制が担保しようとしたもの（導出の正しさ）は、事後に検算で確かめられます。**そしてコーディネータの予想は K 側で「非有意・悪化」＝**実現値と食い違って外れて**います。「とりあえず全部的中」の逆です。
**提案（任意）**: §7 に一句——「登録者は UI（HTML）出力形・コーディネータは同一器材の Python 側出力形で提出した（`derived_table` のキー名が異なる。選択肢空間は同一の `FIELDS` 定数に由来）。両者の導出表は凍結規則で事後に再検算し一致を確認した」。
### (b) `build_adjudication_ui_wsecond.py` の SHA が、同梱のどの文書にも記帳されていません
§7 は「データ生成前に凍結・**SHA記帳**・公開された裁定表UI」と書きますが、**その SHA がどこにあるかを指していません。**`scoring-stage-log` が記帳しているのは `build_**disagreement**_ui_wsecond.py`（工程3の採点不一致UI・**別ファイル**）です。

**提案**: §7 か FREEZE-RECORD に SHA を書けば、「SHA記帳」の主張が自己完結します。
### (c) 確認チェックの対象は**確証層のみ**です
HTML の `gen()` は `p1..p6` の未選択を全てチェックしますが、**確認表に表示される `table()` は `p1, p3, p2, p4a` だけを使います。**`p4b`・`p5`・**`p6`** は `predictions` に入るだけで、**確認チェックの対象になる表には現れません。**
**そして本件で両者が外れたのは、まさに ⑥ です。**
これは器材の欠陥ではありません——docstring が「記述欄（④b⑤⑥）は結果の実現値との等値照合で機械裁定（analyze 側）」と明示しています ✓。**§7 の記述を弱めるものでもなく、一段精密にするものです**: ⑥の**選択肢**は UI で凍結され、⑥の**裁定規則**（≤1件→残余ほぼなし）は UI の確認表には現れず、解析器冒頭のコメントと `apply` の分岐にありました。**記入者は三択を見たが、その三択が実現値とどう照合されるかは見ていません。**
**提案（任意）**: §7 の該当箇所に——「なお UI が記入者に示したのは⑥の**選択肢**までであり、実現値との照合規則（≤1件→残余ほぼなし）は UI の確認表には含まれない（確認チェックの対象は確証層9パターンのみ）。§11-6 の『⑥の裁定規則を次版で FROZEN 本文に昇格』は、この階層差の解消でもある」。
