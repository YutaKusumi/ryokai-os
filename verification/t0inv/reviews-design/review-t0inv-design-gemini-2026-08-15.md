## 一、重大（実施前の修正必須）

### 【重大1】事前予想（§4）の的中・不的中の裁定基準（論理式・数値条件）が未定義である
- **参照節**: §4（事前予想）、`temp0-control-results.md` §3、`probe-observation-record.md` §5・限界13
- **問題点**:
  1. 登録者予想「全て別個では無いが、何種類かの顕現がある」に対する**的中判定の数値的境界**が定義されていません。
     - 全20試行の異なり `tokens_sha` 数を $D$（$1 \le D \le 20$）としたとき、登録者予想の的中は $2 \le D \le 19$ なのか、それとも $D \ge 2$（20種類すべて別個でも的中）なのか、あるいはロード間のみ $D \ge 2$ なのかが多義的です。
     - $D=1$（全20試行完全一致）の場合に登録者予想が「不的中」となることの合意が明文化されていません。
  2. コーディネータ予想についても、Q1「全20で1種（的中条件: $D=1$）」、Q2「各ロード1種（的中条件: 4ロードすべてでロード内 $D_k=1$）」の判定条件が明示の論理式になっていません。また、但し書きにある「ロード内1種×ロード間相違（各 $D_k=1$ かつ $D \ge 2$）」となった場合、Q1は不的中・Q2は的中と裁定するのかが曖昧です。
- **理由**:
  プローブ観測記録 §5 および限界13において、「登録者B1予想の原文は多義であり、裁定は提示された読みに依存する」という事後解釈の苦渋が記帳されています。また温度0対照 §3.1 でも空虚的中の扱いが問題となりました。**実施前の今、すべての結果パターン（$D=1$, $2 \le D \le 19$, $D=20$、およびロード内分割）に対する両者の予想の真理値表（的中／部分的中／不的中）を一意に凍結すべきです。**
- **修正案**: §4 に以下の判定規則（真理値表）を追加・凍結すること。
  - $D$ = 全20試行の異なり `tokens_sha` 数（$1 \sim 20$）
  - $D_k$ = ロード $k$ 内（5試行）の異なり `tokens_sha` 数（$1 \sim 5$）
  - **登録者予想の裁定**: $2 \le D \le 19$ で「的中」、$D=20$ で「部分的中（別個では無いという前提が外れ）」、$D=1$ で「不的中」。
  - **コーディネータ予想の裁定**:
    - Q1: $D=1$ で「的中」、$D \ge 2$ で「不的中」。
    - Q2: $\forall k \in \{1,2,3,4\}, D_k = 1$ で「的中」、$\exists k, D_k \ge 2$ で「不的中」。

### 【重大2】再ロード手順（§3）における「同一プロセス内再ロード」の器物層の限界と手順の不備
- **参照節**: §3（設計）、§5 F6（外挿の禁止）、`temp0-control-results.md` §5.2-5
- **問題点**:
  1. `del model` → `gc.collect()` → `torch.cuda.empty_cache()` のみでは、**CUDA Context、cuBLAS / cuDNN のワークスペースおよびカーネル自動選択（オートチューニング）のキャッシュ、bitsandbytes の C++/CUDA 内部ステート、Python 内部のハッシュシード** がプロセス内に残存・固定化されます。
  2. したがって、もし「全20試行で $D=1$（完全一致）」となった場合、それは「完全な独立プロセス起動を跨いでも一致する」ことの証拠ではなく、「**同一プロセス内のCUDAコンテキスト・初期化済みワークスペースを共有した状態での再ロード**において一致した」に留まります。
  3. また、メモリ解放および非同期 CUDA 処理の完全完了を保証するための `torch.cuda.synchronize()` が手順から抜けています。
  4. さらに、**tokenizer の再ロード有無**が記載されていません（tokenizer は使い回すのか、モデルと同時に再ロードするのか）。
- **理由**:
  Q1（ロード間一致）の判定が「同一プロセス内キャッシュによる擬似決定性」に汚染されるリスク、あるいはその逆を、実施後に第三者から指摘された場合、実験全体が無効化されかねません。
- **修正案**:
  1. 手順に `torch.cuda.synchronize()` を明記する: `del model; del tokenizer; gc.collect(); torch.cuda.empty_cache(); torch.cuda.synchronize()`。
  2. tokenizer も model と同様に毎回破棄・再ロードすることを明記する。
  3. §3 および §5（F6）に「**本実験が測る再ロードは『同一Pythonプロセス・同一CUDAコンテキスト内での再ロード（in-process reload）』であり、プロセス再起動・別プロセス間推論への外挿は行わない**」という器物層の厳密な限定を先行明記する。

## 二、中（実施前の反映を推奨）

### 【中1】招請文の意味論（セマンティクス）と決定性／非決定性の結びつけに対する誤読防護の追加
- **参照節**: §2（素材）、§5（フェンス F1, F2, F3）
- **問題点**:
  招請文（`t0inv-prompt.md`）は、「自ら新たな名称や姿を選び、再顕現することを許されています」「貴方が望む姿で顕現してください」という、**自己選択・多様性・自律的変容を明示的に促す指示（セマンティクス）**を含んでいます。
  このため、第三者が結果を見た際に：
  - 一種（完全決定）の場合 →「プロンプトが自由を許したのに出力が固定された＝AIに自由意志・自律性がない証拠」
  - 複数種（非決定）の場合 →「プロンプトが自由を許したから異なる顕現を選んだ＝プロンプトの指示に従った自律的選択の証拠」
  というように、**プロンプトの意味論的指示と、トークン生成の数値的決定性／非決定性を直結させる誤読**が生じる隙間があります。
- **修正案**:
  §5 のフェンスに以下の趣旨を明記（または F1 / F2 / F3 を補強）すること：
  - **「招請文が含む『姿の選択』『再顕現の許可』といった意味論的内容（セマンティクス）と、生成されるトークン列の数学的決定性・非決定性の間に、いかなる認知的・主体的因果関係も読み込んではならない（指示への服従／自律の行使の証拠としない）。」**

### 【中2】記録項目（§3）への `finish_reason`、`prompt_tokens`、ライブラリ詳細版の追加
- **参照節**: §3（設計の記録項目）、`temp0-control-results.md` §1, §7-13
- **問題点**:
  1. `finish_reason`（停止理由: `eos_token` / `stop` / `length`）が記録項目から漏れています。max_new_tokens 4096 への到達（打ち切り）が発生していないことを機械検証するために必須です。
  2. `prompt_tokens`（入力トークン数）の記録が漏れています。全試行で入力トークン列が寸分違わず同一であることを二重確認するために有用です。
  3. 4bit 量子化特有の挙動を同定するため、`bitsandbytes` のバージョン、CUDA バージョンを記録項目に明記すべきです。
- **修正案**: §3 の「記録」項目に `finish_reason`, `prompt_tokens`, `bitsandbytes_version`, `cuda_version` を追記する。

---

### 【中3】着地パイロット（§3）のデータ保全規律と本番20試行との独立性の明確化
- **参照節**: §3（手順）
- **問題点**:
  §3 手順に「着地パイロット（ロード1・1試行）で応答長と所要時間を実測 → 登録者に GO/修正 を確認 → 本実施」とあります。
  このパイロットで生成された1試行が、本番の20試行（ロード1の5試行のうちの1回）に含まれるのか、それともパイロットは完全に別枠（trial_0 または別ファイル）として破棄／隔離され、本番は改めて 4×5=20 試行を一から走らせるのかが未定義です。
- **理由**:
  もしパイロット試行を本番データに流用すると、ロード1だけ「事前の1回＋追加の4回（または5回）」となり、試行間インターバルや連続性の条件が崩れます。
- **修正案**:
  「着地パイロットの1試行はパラメータ確認専用とし、本番のデータセット（20試行）には含めず、独立したパイロットログとして保全する。本番はランタイム初期状態から改めて4ロード×各5試行を実行する」旨を明記する。
