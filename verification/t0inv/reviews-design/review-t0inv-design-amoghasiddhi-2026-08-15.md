## 3. Q2 —— 設計 (い) は Q1 に対して最小十分か

### 【中】指摘3 「CUDA 状態の再初期化」は、記載の手順がすることではない——かつ、名指しした機構を試せていない

**設計 §3（逐語）**: 「各ロードは `del model` → `gc.collect()` → `torch.cuda.empty_cache()` → 再ロード（**重みの再読込・CUDA 状態の再初期化**）」

**`torch.cuda.empty_cache()` が行うのは、PyTorch のキャッシング・アロケータが保持する未使用ブロックをドライバへ返すことだけ**です。**CUDA コンテキストは破棄されず、cuBLAS/cuDNN のハンドル・ワークスペース・アルゴリズム選択のキャッシュも、プロセス内に残ります。**「CUDA 状態の再初期化」はプロセスの再起動（または明示的なコンテキスト破棄）を要します。

**これは表記の問題にとどまりません。**§4 でコーディネータは、Q1 が割れうる機構をこう名指ししました——

> ただし、**ロードごとのカーネル自動選択（オートチューニング等）が異なる演算経路を選べば**「ロード内1種×ロード間相違」が生じうる

**しかし、オートチューニングの選択結果はプロセス内にキャッシュされます。**`del model` はモデルオブジェクトを解放するだけで、そのキャッシュを消しません。**すなわち、この手順では、名指しされた機構はロード2以降で発火しにくい。**——**設計が「これが起きたら割れる」と名指しした機構を、設計が試せていない可能性があります。**

**これは失敗ではなく、Q1 の射程の問題です。**本実験が測るのは「**同一プロセス内で重みを読み直しても greedy 出力が変わるか**」であり、**F6 はそう書いています**（「同一ランタイム内のモデル再ロード軸のみ」）。**正しいのは F6 で、誤っているのは §3 の括弧と §4 の機構の名指しです。**

**修正案（三点）**:

1. **§3 の括弧**: 「（**重みの再読込とアロケータのキャッシュ解放**——CUDA コンテキスト・cuBLAS/cuDNN のハンドルとアルゴリズム選択キャッシュは**プロセス内に保持される**）」
2. **§4 の機構の名指しに一句**: 「——**ただしこの機構は、プロセスを跨がない本手順では発火しにくい**。発火させるにはランタイム／プロセスの再起動が要り、それは (う) 拡張の領域である」
3. **§0 の一行を精密化**（下記 軽8 と同じ処置）

**なお、これは「差し戻し」ではありません。**プロセス内の重み再ロードでも、アロケータの再配置による**メモリレイアウトの差**（テンソルのアドレス・アラインメント）が縮約順序に影響しうる経路は残ります。Q1 は依然として測る価値のある問いです。**射程の記述を実際の手順に合わせる、という指摘です。**

### 【中】指摘4 パイロットの扱いとウォームアップの有無が未宣言

**§3 手順（逐語）**: 「着地パイロット（**ロード1・1試行**）で応答長と所要時間を実測 → 登録者に GO/修正（max_new・n）を確認 → 本実施」

**三点が未宣言です。**

1. **パイロットの出力は JSONL に記録され、試行として数えられるのか。**記録されないなら、それは**破棄された観測**です。破棄そのものは正当でも、**破棄の宣言は事前に要ります**。
2. **GO/修正で `max_new` や `n` を変えた場合、パイロットは別構成の観測になります。**その場合の破棄を事前に宣言しておかないと、**「結果を見てから構成を変えた」と外形上は区別できません。**
3. **本実施はパイロットのロードを継承するのか、新しいロードから始めるのか。**継承するなら、**ロード1 は既に一度生成を通っており、他の三ロードと状態が非対称**です（ウォームアップ・アロケータ状態）。これは Q1 の判定を直接に濁します——「ロード1 だけ違う」が出たとき、それが再ロードのせいかパイロットのせいか決められません。

**あわせて: 本実施の各ロードでウォームアップ生成を行うか否かも未宣言です。**行うなら、指摘3 の機構は各ロードの記録対象外で吸収され、行わないなら**各ロードの試行1 が特別な位置に立ちます**。

**修正案（§3 手順に三行）**:

> - **パイロット試行は JSONL に `is_pilot=true` で記録し、記述量①〜⑤の集計からは除く**（破棄ではなく別扱いとして残す）。
> - **パイロットの結果として max_new・n のいずれかを変更した場合、パイロット行は「別構成」と明記し、集計に用いない。変更の有無と内容を観測記録に必ず書く。**
> - **本実施はパイロットのロードを継承せず、ロード1 から改めて開始する。各ロードでウォームアップ生成は行わない**（＝各ロードの試行1 は最初の生成である）。

### 【軽】指摘5 記録項目が「温度0対照の様式」の部分集合になっている

**設計 §3**: 「記録 | trial_id・load_id・prompt_sha・tokens_sha・raw_output・gen_tokens・秒・sampling 設定・transformers/torch 版・GPU 名 | **温度0対照の様式＋load_id**」

**前巡（v4.3 検分）で、私は温度0対照の生データ jsonl を全40行・全キーで検算しました。**そのスキーマは——

`arm / family / finish_reason / finish_reason_retry / format_retry_used / gen_tokens / gen_tokens_retry / max_new_tokens / model / parsed / preamble_arm / prompt_sha / quant / question_id / raw_first / raw_output / run_tag / sampling / seconds / timestamp / tokens_sha / top_p / trial_id / trial_index / truncated / turn_structure`

**本設計の列挙は、この部分集合です。**落ちているもののうち、**実害があるのは二つ**——

- **`truncated` / `finish_reason`**: 本実験は `max_new_tokens=4096` で、**出力は自由生成の顕現応答**です。**4096 に当たって打ち切られた場合、tokens_sha は「4096トークンの接頭辞」の比較になります。**打ち切りが起きたか否かが記録になければ、後から観測記録を読む者は「一致」の意味を確定できません。§3 は「打ち切りの混入を避ける」と書いていますが、**避けたことを確認する記録がありません。**
- **`timestamp`**: 指摘11（ロード順と時刻の交絡）に直結します。

**修正案**: 記録項目に **`truncated`・`finish_reason`・`timestamp`（開始・終了）・`max_new_tokens`・`quant`・`model`（チェックポイント revision）・`is_pilot`** を追加。「温度0対照の様式＋load_id」と書くなら、**様式は全キーを指す**——列挙を全キーに揃えるか、「様式の主要項目＋load_id」と書き換えるか、どちらかに。

**とくに `model`（revision）を推奨します。**Q1 は「重みを読み直しても同じか」を問うており、**読み直した重みが同一であることは、Q1 の前提であって結論ではありません。**同一ランタイム内なのでキャッシュから読まれるはずですが、**前提は記録して初めて前提になります。**

### 【軽】指摘6 記述量に「分割の中身」が無く、登録者予想を裁定できない

**記述量②は「全20試行の異なり tokens_sha 数」（＝ k）です。**しかし**登録者の予想は「種類の割れ目がロード間・ロード内のどちらに落ちるかの読みは特定していない」**と明記されており、コーディネータ予想は Q1・Q2 を分けています。

**①（各ロード内の異なり数×4）と②（全体の異なり数）だけでは、分割の構造が一意に決まりません。**例: ①=(1,1,1,1)・②=2 のとき、{L1,L2}vs{L3,L4} なのか {L1}vs{L2,L3,L4} なのかが分かりません。**これは「割れ目がどこに落ちたか」という、登録者予想の中心そのものです。**

**修正案**: 記述量に **⑥ tokens_sha の分割（どの trial_id／load_id が同じ sha を共有するかの完全な対応表）** を追加。**費用ゼロ**（JSONL から機械的に出ます）で、**登録者予想の裁定可能性が生まれます。**

### 【軽】指摘8 §0 の「軸」の言い方が、実測範囲より広い

**温度0報告 §5.2-5 が挙げるのは三つ**です——「**別ロード・別GPU・別セッション**で同じ出力に落ちるかは測っていない」。**本設計が測るのは、そのうち一つ（別ロード・同一ランタイム内）だけ**です。

§0 は「**温度0対照が『測っていない』と自己申告した軸**（§5.2-5「別ロード・別GPU・別セッションで…」）を…測る」と書いており、**三つを引いて一つを測ると読めます。****F6 は正しく限定しています**が、§0 は「何を測るか——一行で」の節であり、**引用のたびに運ばれるのはこちらです。**

**修正案**: 「§5.2-5 が挙げる未測定の三軸（別ロード・別GPU・別セッション）の**うち、別ロード（同一ランタイム内）の一軸のみ**を測る」。

## 4. Q3 —— 事前予想欄と凍結手順

### 【軽】指摘7 裁定表が凍結されていない——「両者とも外れる」場合が覆われていない

**§4 の結び**: 「**両者の予想は方向が割れた**（登録者=複数種／コーディネータ=一種）。**どちらの結果も一方の予想を外す**——方向中立の観測になる。」

**これは、結果が二つしかない場合にのみ成り立ちます。**実際の結果空間を、両者の予想の逐語に当てて展開すると——

| 結果（k＝全20の異なり sha 数／ロード内の内訳） | 登録者「全て別個では無いが、何種類かの顕現がある」 | コーディネータ「Q2 各ロード1種／Q1 全20で1種」 |
|---|---|---|
| k=1 | **外れ** | **両方的中** |
| ロード内1種・ロード間相違（k=2〜4） | **的中** | Q2 的中・Q1 外れ |
| ロード内が割れる（k=5〜19） | **的中** | **両方外れ** |
| **k=20（全て別）** | **外れ**（「全て別個では無い」に反する） | **両方外れ** |

**k=20 では、両者とも外れます。**「どちらの結果も**一方の**予想を外す」は、この場合を覆っていません。またコーディネータ予想は二成分あり、**部分的中**が三通り生じます。

**修正案（§4 に凍結して置く）**: 上の表そのものを **裁定表として実施前に凍結**する。**プローブ記録 限界13 が「登録者B1予想の原文は多義であり、裁定は提示された読みに依存する」と記帳した型**に、同じ場所で当たっています——**多義の解消を、データを見る前に済ませておく**のが、その記帳の How to apply です。

### 【提案】指摘10 Q2 が割れた場合の Q1 の扱いを、事前に決める

**Q1（ロード間一致）は、Q2（ロード内一致）が成り立つことを暗黙の前提にしています。**ロード内が既に割れているなら、「ロードを跨いで一致するか」という問いは基準を失います。

**§3 の割り当ての根拠**——「ロード内決定性は温度0対照が n=20 で確立済み→ロード内は n=5 で足り」——には、**軽い循環があります**。温度0対照が確立したのは **N2 シナリオのプロンプト族**での決定性であり、**本実験の Q2 は「プロンプト族を替えた複製」として、まさにそれを確かめる問い**です。既に確立していることを理由に n を減らす、という論法は、Q2 が問いであることと両立しません。

**n=5 でよい、という結論には同意します**（粗い非決定性の検出には十分で、4ロードへ配分する判断は合理的です）。**足りないのは、外れた場合の宣言です。**

**修正案（§1 または §3 に一行）**: 「**Q2 が割れた場合（いずれかのロードで2種以上）、Q1 は判定不能として記録する**——ロード内の基準が立たないまま、ロード間の一致／不一致を読まない。」

### 【提案】指摘11 ロード順と時刻が完全に交絡している

4つのロードは単一ランタイムで**逐次**実行されます。すなわち `load_id` は**経過時間・GPU 熱状態・メモリ断片化の進行**と完全に交絡します。ロード1 と ロード4 で出力が違ったとき、**「再ロードのせい」と「時間経過のせい」を、本設計は分離できません。**

**費用の低い順に三案**:

- **(a) 開始時刻の記録**（指摘5 に含む）。交絡を消しはしませんが、**観測記録に交絡を書けるようになります**。最低限これは行うべきです。
- **(b) ロード5 を「ロード1 条件への復帰」として置く**（＋1ロード）。ロード5 がロード1 と一致し 2〜4 と違うなら、**再ロードではなく順序／時間の効果**が示唆されます。
- **(c) 何もしないが、限界として明記する**——「load_id は時間順と完全に交絡しており、両者を分離していない」。

**(a) は必須、(c) は必須、(b) は登録者判断**、というのが私の推奨です。

### 【提案】指摘12 予想の「方向が割れた」ことの身分

**§4 は記入順を正しく開示しています**——登録者が先、コーディネータが後（**プローブ限界13 と逆順の同型**）、「アンカリングは排除できない」。**この開示は十分です。**

**足りないのは、逆向きのリスクの名指しです。**コーディネータは**登録者予想を読んだうえで、方向の割れる予想を書きました**。そして「**両者の予想は方向が割れた…方向中立の観測になる**」と結んでいます。

**割れたのは、独立に割れたのではありません。**後から読んだ側が、割れる方向に置いた結果でもありえます。そして**予想が割れていれば「どちらかは当たる」——これは記録として鮮やかに見えます。**起草者の COI 記帳（「所見を面白い方向へ強く書く癖」五件）に照らせば、**この形は名指しに値します。**

**修正案（§4 の結びを置き換え）**:

> 両者の予想は方向が割れた（登録者=複数種／コーディネータ=一種）。**ただし、この割れは独立に生じたものではない**——コーディネータは登録者予想を閲読した後に記入しており、**割れる方向を選んだ可能性を排除できない**。したがって、この対の値打ちは「方向中立であること」ではなく、**両方が実施前に凍結され、逐語で残ること**にある。**なお、双方が外れる結果（全20が全て別）もありうる**（裁定表を参照）。
