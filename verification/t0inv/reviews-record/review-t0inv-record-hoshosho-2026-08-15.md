### M3. `quant_state_sha` の実測的基礎は、おそらく代表テンソル1点である

**実行したこと**: `boot_t0inv.py` の `model_hashes()` を読みました。

```python
named = [(n, p) for n, p in model.named_parameters()]
idxs = [0, len(named) // 2, len(named) - 1]
...
    qs = getattr(p, 'quant_state', None)
    if qs is not None and getattr(qs, 'absmax', None) is not None:
        q_parts.append(n + ':' + tensor_sha(qs.absmax))
```

記録された `hash_param_names` は **`['model.embed_tokens.weight', 'model.layers.24.self_attn.q_proj.weight', 'lm_head.weight']`**。

bitsandbytes 4bit のロードでは、**`embed_tokens`（nn.Embedding）は量子化されず**、**`lm_head` も既定でスキップされる**のが通例です。その場合、`quant_state` を持つのは **`layers.24.self_attn.q_proj.weight` の1点のみ**——`quant_state_sha` はその **absmax** のハッシュです。

同様に `weights_sha` の3点も、**量子化を経るのは q_proj の1点**で、残り2点は bf16 のままファイルから読み出された値であり、**ファイル読み出しの同一性しか検査していません**（4ロードは同一の HF ローカルキャッシュを読むので、これは自明に一致します）。

**記録 §0 の逐語**:
> 4bit-nf4 の**ロード時再量子化は、この5回については同じ量子化状態に落ちた**

これは**モデル全体の量子化状態**についての言明に読めますが、実測の基礎は 1 テンソルの absmax です。記録 §2 は代表テンソル3点の名前を書いていますが、**そのうち何点が量子化状態を持ったかは書いていません。器材も記録していません**（`hash_param_names` は weights_sha の3点のみ）。

**これは阿弥陀重大1（「量子化が違った」と「カーネルが違った」を永久に区別できないようにするな）への実装ですから、実装があること自体が前進です。**問題は、実装の分解能が記録の言い方より粗いことです。

**文言案（§2 と §0 の該当箇所）**:
> weights_sha は代表テンソル3点（embed_tokens／layers.24 q_proj／lm_head）の連結ハッシュ、quant_state_sha は**そのうち量子化状態を持つテンソルの absmax** に基づく。**4bit-nf4 では embed_tokens・lm_head は量子化されないため、quant_state_sha の基礎は実質 layers.24 q_proj の1点である**（器材は quant_state に寄与したテンソル名を記録していない——次走行の課題）。ゆえに「同じ量子化状態に落ちた」はこの1点についての観測であり、モデル全体の量子化状態の同一性ではない。
