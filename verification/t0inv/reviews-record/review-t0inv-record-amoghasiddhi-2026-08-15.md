**記録の記述**:

**修正案**: 「温度0対照キーとの差集合＝**`{raw_output}` のみ**（F14 により raw 分冊へ分離・それ以外は上位互換）」

### 【軽】指摘4 `finish_reason` は `truncated` の導出値であり、独立の検査ではない

**器材（124〜125行）**:
```python
truncated = gen_tokens >= MAX_NEW
finish_reason = 'length' if truncated else 'stop'
```

**`finish_reason` は生成 API の停止理由ではなく、`truncated` から一意に決まる派生値です。**

**§2 は「truncated 0・finish_reason≠stop 0」を二つの検査として並べていますが、構成上これは一つの検査です。**同様に §1 の「finish_reason 全て stop」は、「gen_tokens < 4096」以上のことを言っていません。

**実質的には問題ありません**（gen=690 < 4096 なので EOS で停止したことは確かです）。**ただし、二つの独立な確認があるように見える書き方**は、この記録の精度水準に照らして直す価値があります。

**修正案**: §2 を「truncated 0（＝ `finish_reason` も全て stop——本器材では `finish_reason` は `truncated` からの導出値であり、独立の信号ではない）」

### 【軽】指摘5 「パイロットと本実施は同一プロセス」は、同梱物からは検証できない

**§6-5（逐語）**: 「**パイロットと本実施は同一プロセス**: 本実施のロード1〜4 は、パイロット（load 0）が既に生成を通した後のプロセス内にある。」

**この限定は、記録を弱める方向の申告であり、その姿勢は正しいものです。**しかし**私は、同梱データから同一プロセスであることを確認できませんでした。**

理由: 器材の `_prev_end` はモジュール水準の変数で、`exec` のたびに初期化されます。実際、**本実施の最初の `gap_seconds` は 0.0** であり、これはプロセスが継続していても新規でも同じです。パイロット終了（05:19:00Z）から本実施開始（05:40:11Z）まで**約21分の空白**があり（登録者 GO の待ち時間——§1 の記述と整合）、この間にプロセスが継続していたか否かを示す痕跡は、データにありません。

**なお、どちらであっても記録の主張は成り立ちます**（同一プロセスなら §6-5 のとおり、新規プロセスなら限定が一つ消えるだけ）。**指摘は「検証できない」であって「誤り」ではありません。**

**提案（次回の器材へ）**: `os.getpid()` またはモジュール読み込み時に生成する UUID を各行に記録する。**費用ゼロで、プロセス同一性が第三者に検証可能になります。**

### 【軽】指摘6 試行順序が全ロードで固定されており、族の効果と順序効果が分離されていない

**器材（176〜179行）**: 各ロードは必ず「招請文 ×N → 短対照 ×2」の順です（コメントに「順序は全ロード同一」と明記）。

**すなわち、短対照は常に招請文5試行の後の状態で走っています。**「短い生成でも割れなかった」（§5 長さの層）という観察は、**5回の長い生成を通した後の状態についてのもの**であり、ロード直後の短い生成については何も言っていません。

**D=1 なので実害はありません**が、**§6 は「分離されていないもの」を並べる節**です。§6-6 は「短対照の分離機能は未発動」と書いていますが、これは D=1 だったからであり、**順序が固定であることは D の値によらない設計上の限定**です。

**修正案（§6-6 に一句）**: 「…未発動（§5）。**なお試行順序は全ロードで固定（招請文→短対照）であり、族の効果と順序効果は本設計では分離されていない。**」

### 【軽】指摘7 §1 の「ロード1のみ HF キャッシュ直後」は、§5 の外に置かれた機構帰属である

**§1 の表（逐語）**: 「load_seconds＝217.6／248.6／249.7／250.4 秒（**ロード1のみ HF キャッシュ直後**）」

これは 217.6 と ~249 の差（約13%）についての**原因の説明**です。**記録は §5 に「機構についての記述（原因主張はしない——F2 の系）」という節を設け、そこで慎重に扱っています。**§1 の表の括弧は、その節の外にある機構帰属です。

**ごく軽微ですが**、この記録の作法（機構は §5 に集約し、原因を主張しない）に照らせば、「（ロード1 は他より約30秒短い——原因は本記録では特定しない）」とするのが一貫します。

### 【提案】指摘8 器材の来歴——「初版のバグ」が設計にも記録にも無い

**`boot_t0inv.py` の 180〜181行（逐語）**:

> ```
> # in-process reload の解放手順(設計 §3-1)。注意: 関数に渡して del すると呼び出し側の参照が
> # 残り実体が解放されない(初版のバグ・二巡目見直しで修正)——この関数内で直接 del する。
> ```

**すなわち、器材の初版には「del しても実体が解放されない」バグがあり、二巡目の見直しで修正されました。**

**これは逸脱ではありません**——修正は凍結前であり、凍結 SHA は一致し、実際に走ったのは修正版です。§8「逸脱なし」は正しい。

**しかし、記録すべき事実だと考えます。**もしこのバグが残っていれば、**「再ロード」は実体の解放を伴わず、本実験は跨ぎ軸を測っていなかった**——**実験そのものが無効だったのに、出力は同じく一致し、記録は同じ結論を書けた**からです。

**私が検索した限り、設計にも記録にも「バグ」「初版」「解放され」の語はありません**（設計0件／記録0件。設計に「二巡目見直し」の語は1件ありますが、別文脈です）。**器材のコメントにだけ残っています。**

**これは、この計画が §9 で扱ってきた主題そのものです**——「捕まえたのは機械検査ではない」「訂正もまた、検分されなければ新しい誤りを作る」。**器材の見直しが実験の有効性を救った、という記録は、残す価値があります。**

**修正案（§8 または §6 に一行）**:

> **器材の来歴**: `boot_t0inv.py` の初版には、モデル解放を関数外で行うと呼び出し側の参照が残り実体が解放されない不具合があり、**凍結前の二巡目見直しで修正した**（器材内コメントに記載）。修正前の器材で走らせていた場合、「再ロード」は実体の解放を伴わず、**跨ぎ軸を測っていないまま同じ結論を書きえた**。凍結・実施されたのは修正版である（SHA `A7C25B1D88FE34C0`）。

### 【提案】指摘9 §6 に「D=1 のとき言えることは、割れたときより弱い」を一行

設計 F5 は「**割れた場合と一致した場合で、言えることの強さが違う**——割れれば『この構成で割れることがある』が言える（存在）。一致しても『一致する』は言えない（全称）」と凍結しています。
