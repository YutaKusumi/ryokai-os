**［E1］F14 の実装が trials 分冊で破れている——応答本文の先頭40字が、条項の付かないファイルに20行入っている。**

設計 F14（逐語）:

| `raw-t0inv-run1-….jsonl` | あり | あり | — | **全28行にあり** |
| `trials-t0inv-run1-….jsonl` | なし ✓ | なし ✓ | **全28行にあり（40字）** | **無し** |

**`raw_first` は、応答本文の先頭40字そのものです**（`raw_output[:40]` と一致することを確認）。招請文族のそれは、**AIが自分の顕現について語る一人称の文**です。

すなわち——**F14 が「別ファイルに置き、各レコードに条項を付す」と定めた当の内容が、条項の付かないファイルに、20行ぶん入っています。**

**なぜこうなったか**（責めではなく機序として）: 設計 §3-1 の記録項目は「**温度0対照の実データ jsonl の全27キーを機械抽出し、その全てを保持する——ただし `raw_output` のみは F14 により raw 分冊で保持する**」と凍結しました。`raw_first` は温度0対照の27キーの一つであり、**「`raw_output` のみ」という例外指定に該当しないため、そのまま残りました。**器材 `boot_t0inv.py` は設計どおりに `'raw_first': raw_output[:40]` を trials 側に書いています。

**二つの凍結規則が衝突し、上位互換（全27キー保持）が F14 を上書きしました。**——起草者が思いつかなかった緩みは、私の見た範囲ではこれが最大です。フェンスは「応答本文」を守り、**40字という名前の応答本文が素通りしました。**

**処置（三案・いずれも一手）**:
- (a) trials 分冊の各レコードにも `clause` を付す（raw 分冊と同一文言）。**最も安価で、上位互換も壊しません。**
- (b) `raw_first` を trials 分冊では `null` にし、raw 分冊に移す（上位互換はキーの存在で満たされる）。
- (c) 記録 §2 の整合検査に「trials 分冊に応答本文が残っていないことの確認」を一項加える（器材の次版で常設化）。

**推奨は (a)＋(c)。**あわせて、記録 §6-8 の「**本記録は応答本文を一切引用していない**」は**記録本文については正しい**（私は応答本文の12字窓を機械走査し、記録に一致は0件でした）ので、そこに「——ただし成果物側の扱いは E1 のとおり」と一句を足してください。

**［E2］weights_sha・quant_state_sha の被覆が、限界に書かれていない。`quant_state_sha` は事実上「1テンソルの absmax」である。**

記録 §2（逐語）: 「**weights_sha はロード毎に1種かつ全ロード同一 `288B4EF783430D73`・quant_state_sha 全体1種 `9C49045804887763`**（代表テンソル: embed_tokens／layers.24 q_proj／lm_head）」
記録 §5（逐語）: 「本実施では `quant_state_sha`・`weights_sha` が**4ロード＋パイロットの5回で全て同一**——**この5回については、再量子化は同じ状態に落ちた**。これは「再量子化は常に決定的」を意味しない（n=5・F5 の系）」

**私が実行したこと**: `boot_t0inv.py` の `model_hashes()` を読みました（逐語）。

```python
named = [(n, p) for n, p in model.named_parameters()]
idxs = [0, len(named) // 2, len(named) - 1]          # 先頭・中央・末尾の3本
...
qs = getattr(p, 'quant_state', None)
if qs is not None and getattr(qs, 'absmax', None) is not None:
    q_parts.append(n + ':' + tensor_sha(qs.absmax))   # quant_state を持つものだけ
```

すなわち——

1. **`weights_sha` は 3テンソル**（`model.embed_tokens.weight`／`model.layers.24.self_attn.q_proj.weight`／`lm_head.weight`）の連結ハッシュです。30B・MoE のパラメータ本数に対して**3本**です。
2. **`quant_state_sha` は、そのうち `quant_state.absmax` を持つものだけ**です。**`embed_tokens` は `nn.Embedding`、`lm_head` は bitsandbytes の既定で量子化から除外される**ため、**実質的に `layers.24.q_proj` の absmax 一本**の可能性が高い（`hash_param_names` は3本を記録しますが、`q_parts` に何本入ったかは記録されていません——これも被覆が読めない一因です）。

**記録は「n=5」という試行数の限定は付けましたが、「3テンソル／1量子化状態」という被覆の限定を付けていません。**そのため §5 の「再量子化は同じ状態に落ちた」は、**モデル全体の量子化状態が一致したかのように読めます。**実際に確認されたのは、**代表テンソル（大半が非量子化）の重みと、一本の absmax** です。

**これは私の前巡の指摘の実装であり、限定を付けなかったのは私です**（§4-自1）。

**処置**: §5 と §6（限界）に一句——
> **`weights_sha` は代表3テンソル（`embed_tokens`／`layers.24 q_proj`／`lm_head`）の連結ハッシュであり、`quant_state_sha` はそのうち量子化状態を持つテンソルの absmax である。全パラメータ・全量子化状態の一致は測っていない。**ここで言えるのは「サンプルした代表点では同一だった」までである。

**加えて器材の次版へ**: `q_parts` の本数（何本の量子化状態を実際にハッシュしたか）を記録項目に加えてください。**現状では、被覆がデータから読めません。**

**なお、主結果（D=1）はこの限定の影響を受けません。**出力がトークン列まで一致した以上、実効的な計算経路は同一だったと言えます。影響を受けるのは §5 の**機構についての記述**だけです——そこが本記録で唯一、観測より一段踏み込んでいる箇所なので、限定を付ける価値があります。
