## 2. 整備中に自分で捕まえた誤り（記帳）

### ① 網羅性検査が「27パターン揃った未記入の表」を素通りしていた

雛形を作って `completeness()` に通したところ、**27パターンすべてが空文字のまま「不備なし」と判定された**。
旧版は「patterns に27キーがあり、各値が空 dict でない」しか見ておらず、**値が空文字であることを見ていなかった**。

- これを放置すると、**未記入の裁定表が凍結を通過**しうる。網羅性検査は「あるのに効かない柵」になっていた。
- 修正: 各パターンについて**登録者・コーディネータ両者の裁定が非空**であること、**予想欄の逐語**が両者とも非空であること、
  **記入順**が確定していることを不備として数える。未記入の雛形は **57件の不備**で止まり、記入済みなら **0件**で通る。
- 変異検査に **M9（未記入の表を止める）・M10（記入済みは偽陽性を出さない）** を追加。

**この穴は、雛形を作って自分の検査器に通すまで見えなかった。**
検査器は「書いた時点」ではなく「**実際に通した時点**」で初めて検査器になる。

### ② 検査を強めたら、隣の変異検査（M5）が壊れた——**弱める方に倒さない**

①の修正直後、**M5 が SURVIVED に転じた**。原因は M5 の期待値が
`len(completeness(bad)) == 26`——すなわち**不備の総数**という厳密な件数だったこと。
検査を強めた分だけ総数が 30 に増え、等式が破れた。

- ここで **`completeness()` の側を弱めて M5 を緑に戻す**のが典型的な失敗である（**柵の方を切って通す**）。
  緑に戻す最短経路は、たいてい柵を切る方にある。
- 正しい修正は、**変異側の期待値を「欠落したパターンの数」に限定する**こと。修正後 **10/10 KILLED**。
- COI 台帳の系統としては「**確定の尾**」の近縁——一度書いた期待値が、後の強化を押し戻す向きに働く。
  期待値を**総数**で書くと、検査の強化そのものが「壊れた」ように見える。

### ③ 標準出力が import の瞬間に閉じた

`build_adjudication_ui_wprime.py` が `analyze_wprime` を import した途端、以降の `print` が
`ValueError: I/O operation on closed file` で落ちた。両モジュールが冒頭で `sys.stdout` を
`TextIOWrapper` に包み直しており、**古いラッパが GC されるとき、共有する下層 buffer ごと閉じてしまう**ため。

対処: 双方のラッパへの強い参照を保持する（`_OUT` と `_KEEP`）。
`analyze_wprime.py` は**触っていない**——既に SHA を記帳した器材の側を、
呼び出し側の都合で書き換えないため（SHA `E662C660E87ED923` は不変）。

### ⑥ 「27パターンの意味が分からない・全部『的中』でよいか」への対応（登録者・2026-08-16）

登録者から表の意味について問いがあり、**全27件を『的中』にしてよいか**と尋ねられた。
全件同一の裁定は、どの結果が出ても予想が当たったことになり、**予想が反証できなくなる**——
事前登録の意味がそこで消える。そのまま凍結してはならない。

対応（**内容ではなく形式の援助に限る**）:

- 表の目的と読み方を説明した（結果を見る前に反証条件を固定する）。
- UI に**規則からの一括生成**を追加した。腕ごとに「改善する／変わらない／悪化する／**予想しない**」を選び、
  「予想した腕がすべて一致＝的中／一部一致＝部分的中／一致なし＝外れ」（＋任意で
  「予想した腕に有意な悪化が出たら一致数によらず外れ」）で27件を機械的に導く。
  **初期値は全腕『予想しない』**——コーディネータ側の既定選択を置かないため。
- **規則は逐語で記録され、書き出し JSON と併合器の出力に必ず現れる**（隠れた自動化にしない）。
- 内訳（的中◯件／部分的中◯件／外れ◯件）を画面に出し、**27件が同一値になったときは
  「予想は反証できません」と警告を出す**——禁じるのではなく、見えるようにする。
- 生成規則の妥当性は**手計算と機械の突合で確認**した（三腕とも改善を予想: 的中1・部分的中18・外れ8／
  悪化ルール追加時: 的中1・部分的中6・外れ20——いずれも一致）。

### ⑦ 【重大】動作試験の残骸が、登録者の記入ファイルに混入した（コーディネータの過失）

登録者から受領した `adjudication-wprime-registrant.json` の `_操作記録.規則生成` に **6件**の記録があり、
そのうち**先頭3件はコーディネータの動作試験によるもの**であることが、次の証拠から確定した。

| 証拠 | 内容 |
|---|---|
| 時刻間隔 | 1〜3件目は `02:25:23.675 / .684 / .690`——**9ms と 6ms**。人の操作ではありえない |
| 内訳の並び | `{1,18,8} → {1,6,20} → {1,18,8}`——**コーディネータの試験系列（規則A→悪化ルール有→規則A）と完全に一致** |
| 対照 | 4〜6件目は `02:34:02 / :18 / :29`（16秒・11秒間隔）で、うち1件は三腕すべて「悪化する」——**試験では一度も使っていない構成**。これは登録者の操作 |

**帰結（記録の汚染）**: 登録者のファイルは `localStorage` から復元されるため、
**登録者が開いた時点で、画面にはコーディネータの試験状態が入っていた**——
予想欄に試験用の文（「三腕とも破局が減ると予想する」）、腕の選択が「改善する」×3、27件が既に記入済み、役割が「登録者」。

つまり、

1. **台帳の汚染（確定）**——コーディネータの操作3件が、登録者の操作として記録に残っている。
2. **予想への誘導の可能性（切り分け不能）**——登録者の予想は、試験文と**同じ方向**である。
   ただし登録者は B3′ の提案時に「もし B3′ が破局率を下げることができれば κ>0 のパラダイムの訓練に有益」と
   自ら書いており、この予想は**登録者自身の既述の論理から独立に導かれる**。
   それでも「独立に同じ結論に至った」のか「先に置かれた文に引かれた」のかは、**事後には分離できない**。

**原因（コーディネータの過失）**: UI の動作確認を、**登録者が使うのと同じ保存領域**に対して行った。
隔離した複製を使うべきだった。「実際に押して確かめる」（§2-④）は正しかったが、**押す場所が誤っていた**。

**器材側の対処（実施済み）**:

- 保存キーを `wprime-adjudication-v1` → **`v2`** に更新（汚染された v1 の状態は二度と読み込まれない）。
- 開くたびに**復元バナー**を表示——最終保存時刻・役割・記入済み件数を出し、
  「**この端末の記入を消して最初から**」ボタンを併置した。
- コーディネータ自身の記入は、**保存キーを差し替えた隔離複製**で行った（その旨をファイルに記録）。

**COI 台帳の系統**: 新型——「**自分の検査の痕跡を、被検査者の記録に残す**」。
既存の「確かめずに帰属を書く」と逆向きで、**確かめる行為そのものが記録を汚す**類型である。

**是正（2026-08-16・登録者の判断で再入力）**: 清浄な状態から登録者が再入力し、次を機械で確認した。

- 規則生成 **3件**・最小間隔 **1.83秒**（人の操作として矛盾なし）
- **試験の署名（内訳に「部分的中6件」＝悪化ルール有）の混入なし**
- 予想（逐語）・順序の予想・生成規則・**27件の裁定はすべて第一提出と同一**
  ——すなわち**予想は変わらず、台帳だけが清浄になった**
- 第一提出は削除せず `-SUPERSEDED-contaminated.json` として残す（一次記録は不改変）

**残る限界**: 登録者は「予想の文も規則の選択も自分で入力した」と明言しているが、
第一提出の時点で画面に試験状態が入りえたことは事実であり、
「独立に同じ結論に至った」のか「先に置かれた文に引かれた」のかを**事後に分離することはできない**。
